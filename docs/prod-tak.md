# Production TAK integration

This document describes how to wire the BattleLog (`blapi`) service inside the
`docker-rasenmaeher-integration` production stack so that the TAK code added on
the `tak-integration` branch can reach the production TAK server.

The BattleLog code itself is **safe by default**: `TAK_ENABLED` defaults to
`false`, so updating the production stack's BattleLog submodule pointer alone
does not start any TAK client, open any socket, or change `/api/tak/*` behavior.
The integration only activates when the production compose file passes the
environment listed below to the `blapi` service.

## What the production stack already provides

- A TAK server reachable as `takconfig:8089` on the `taknet` Docker network. All
  TAK sidecars share `takconfig`'s netns.
- A trusted RM CA chain at `/ca_public/ca_chain.pem`, already mounted into the
  `blapi` container via the `ca_public` named volume.
- An RM-issued mTLS client cert and key, generated by `kw_product_init` during
  `blapi`'s first run and persisted to:
  - `/data/persistent/public/mtlsclient.pem`
  - `/data/persistent/private/mtlsclient.key`
  The subject CN is `battlelog.<SERVER_DOMAIN>` and the cert is signed by the
  RM intermediate CA that TAK's truststore trusts.
- A shared `postgres` service that hosts the TAK Server `cot_router` schema in
  database `tak` (user `tak`, password `${TAK_DATABASE_PASSWORD}`). The TAK DB
  poller can read marker rows from there directly.

No new client certificate has to be minted. BattleLog reuses its existing
`mtlsclient` cert for the TAK TLS stream.

## Compose wiring required in `docker-rasenmaeher-integration`

Add the following to the `blapi` service in `docker-compose.yml` (only the
delta is shown):

```yaml
  blapi:
    environment:
      <<: [*bldbconfig_env]
      TAK_ENABLED: "true"
      TAK_HOST: takconfig
      TAK_TLS_SERVERNAME: *takdomain
      TAK_STREAM_PORT: "8089"
      TAK_STREAM_TLS: "true"
      TAK_REJECT_UNAUTHORIZED: "true"
      TAK_CLIENT_CERT_PATH: /data/persistent/public/mtlsclient.pem
      TAK_CLIENT_KEY_PATH: /data/persistent/private/mtlsclient.key
      TAK_CA_PATH: /ca_public/ca_chain.pem
      TAK_DB_POLL_ENABLED: "true"
      TAK_DB_HOST: postgres
      TAK_DB_PORT: "5432"
      TAK_DB_NAME: *takdbname
      TAK_DB_USER: *takdbuser
      TAK_DB_PASSWORD: *takdbpass
    networks:
      - productnet
      - intranet
      - dbnet
      - taknet
    depends_on:
      rmnginx:
        condition: service_healthy
      rmapi:
        condition: service_healthy
      postgres:
        condition: service_healthy
      takmsg:
        condition: service_healthy
```

No new volumes are needed — `ca_public` and the `blapi_data` (persistent)
volume already cover both required paths.

## TAK user-registration caveat

BattleLog will present its own `mtlsclient` certificate (CN
`battlelog.<SERVER_DOMAIN>`). TAK trusts the RM CA, so the TLS handshake
itself succeeds. However, `takintegration` only registers its own
`mtlsclient` cert (CN `tak.<SERVER_DOMAIN>`) as a TAK admin during
`tak_init`. Depending on the TAK Server's authentication configuration in
this deployment, BattleLog's CN may need to be enrolled as a TAK user (or
admin) before TAK accepts CoT traffic on the stream.

If TAK rejects the BattleLog connection, two follow-up options exist (both
outside the scope of this BattleLog change):

1. Add a one-time admin step (e.g. in `takintegration`'s `tak_init`) that
   copies `blapi`'s `mtlsclient.pem` into `/opt/tak/data/certs/files/` and
   registers its CN as a TAK user — mirroring how `takintegration` already
   self-registers `mtlsclient` today.
2. Or mint a dedicated `blapi.p12` from the TAK CA and point
   `TAK_CLIENT_P12_PATH` / `TAK_CLIENT_P12_PASSWORD` at it instead.

## Verifying behavior without TAK enabled

When the wiring above is **not** applied:

- `TAK_ENABLED` falls back to `false`.
- `TakService.start()` is a no-op (`backend/index.js`).
- `GET /api/tak/markers` and `GET /api/tak/chat` return disabled snapshots
  (`status: "disabled"`, empty arrays).
- `POST /api/tak/*` returns `503`.

This means simply bumping the BattleLog submodule pointer in the production
stack — without applying the compose delta — is a no-op for users.

## Local TAK development is unaffected

See [`local-tak.md`](local-tak.md). The local override
(`docker-compose.tak.yml`) keeps its own service names (`takserver_config`,
`takdb`) and `.env.tak` defaults. Nothing about the production wiring above
changes the local workflow.
